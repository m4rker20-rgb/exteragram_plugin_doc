# 16. Публикация плагина

Как довести плагин до релиза и где его распространять.

## Формат распространения

- **Обычный плагин** — один `.py`-файл. Многие авторы переименовывают его в `.plugin` — расширение‑маркер, содержимое остаётся валидным Python-кодом.
- **Elyx-плагин** — ZIP-совместимый архив `.elyx` / `.eaf` (см. [11](11-elyx-structured-plugins.md) и [12](12-elyxbuilder-and-dev-server.md)).

## Чеклист перед релизом

### Метаданные

- [ ] `__id__` соответствует правилам (2–32 символа, с буквы, `[a-zA-Z0-9_-]`) и **не меняется** между версиями;
- [ ] имя файла на устройстве = `__id__ + ".py"`;
- [ ] `__app_version__` / `__sdk_version__` указывают версии, на которых реально тестировали;
- [ ] `__requirements__` содержит только pure-Python пакеты;
- [ ] `__description__` читаемо и в Markdown корректно;
- [ ] `__icon__` указывает на существующий стикерпак (`СтикерПак/индекс`).

### Поведение

- [ ] включение/выключение не оставляет мусора (хуки, меню убираются SDK; потоки/наблюдатели — в `on_plugin_unload`);
- [ ] обновление с предыдущей версии не сбрасывает настройки пользователя (id стабилен);
- [ ] мультиаккаунт: ответы из хуков идут через `self.client(account)`;
- [ ] нет блокировки UI-потока в горячих путях;
- [ ] логи не содержат чувствительных данных пользователя.

### Архив (для Elyx)

- [ ] `refmap.yml` в корне архива, без директории-обёртки;
- [ ] нет `.git/`, `__pycache__/`, `builds/`, секретов, локальных логов;
- [ ] байткод собран Python 3.11;
- [ ] английская локаль присутствует всегда (fallback);
- [ ] чистая установка из архива проверена (не только live reload).

## Безопасность плагина

Плагины исполняют Python-код с доступом ко всему приложению — относитесь к опубликованному коду ответственно:

1. **Не встраивайте секреты** — токены, ключи, пароли в `.py`/`.elyx` читаются любым.
2. **Зависимости — исполняемый код**: пинуйте версии, не тяните пакеты «на глаз».
3. **Загрузка кода по сети** — самый рискованный паттерн. Если библиотека грузится с URL — привязывайтесь к неизменяемому коммиту и проверяйте SHA-256 (как сделано в PACLibs secure loader).
4. **Дайте пользователю понять, что делает плагин** — честное описание, открытый исходник.

### Аудит

[Pluggy Bot](https://t.me/pluggy_robot) выполняет автоматический статический анализ плагинов exteraGram и генерирует отчёты безопасности (`secure.md`), которые многие каталоги (например, awesome-telegram-plugins) прикладывают к каждому плагину. Прогонка плагина через аудит перед релизом — хорошая практика и доверие пользователей.

Вели безопасность репозитория по образцу [awesome-telegram-plugins](https://github.com/makarworld/awesome-telegram-plugins): исходник плагина + `README.md` (для пользователей) + `docs.md` (для разработчиков) + отчёт безопасности + папка `releases/vX.Y.Z/` с changelog.

## Где публиковать

| Площадка | Что это |
|---|---|
| **Telegram-канал exteraGram Plugins** | Официальный канал плагинов |
| **exteraGram Plugins (supporters)** | Плагины от саппортеров, мейнтейнер @itsv1eds |
| **Dotted** | Плагины @exteraDev |
| **zwyPlugins** | Плагины @zwylair |
| **GitHub** | Свой репозиторий; удобно давать raw-ссылки — менеджеры плагинов умеют качать напрямую (например, через `raw.githubusercontent.com` или CDN типа jsDelivr) |
| **Kangel Plugins Store** | Крупнейший каталог (775+ плагинов): репозиторий [Kangel-Plugins/Plugins-Store](https://github.com/Kangel-Plugins/Plugins-Store) с зеркалами (GitHub/Codeberg/GitVerse/git.kangel.xyz); для установки используется [Kangel Plugins Manager](https://github.com/Kangel-Plugins) |
| **Kangel Plugins Manager и подобные** | Внутриигровые магазины плагинов — как правило, принимают плагины через PR в каталог |

Как устроен каталог Kangel (из разбора KPM 1.6.0): файл `store.json` содержит запись на каждый плагин — `url`, `name`, `version`, `author`, `description`, `icon`, `min_version`, `requirements`, `dependencies`, **SHA-256 `hash`** и RSA-подпись (`signature`, подписывается строка `plugin_id:version:hash`, публичный ключ зашит в менеджер). Файлы лежат в `Plugins/<id>.plugin`, старые версии в `legacy_versions/`. Плагин-файл при этом остаётся валидным Python — менеджеры качают его напрямую.

Практика: держите в канале пост с прямой ссылкой на файл (`https://t.me/.../file`) или GitHub-raw — большинство менеджеров плагинов устанавливают по таким ссылкам.

## Версионирование

- `__version__` — строки вида `"1.2.3"`; можно с суффиксами (`"1.0 [beta]"`, `"4.0.0 [pre-release]"` — так делают в сообществе), но для машинной обработки лучше чистый semver.
- Меняйте версию при каждом публичном релизе.
- Смена `id` = новый плагин (пользователи получат дубликат) — избегайте.

## Права и лицензии

- Указывайте лицензию в репозитории (MIT — самый частый выбор в сообществе).
- Если использовали чужие фрагменты кода — упомяните автора в описании (распространённая практика: «указать @автора в описании своего плагина в благодарность»).
- Соблюдайте лицензии бандл-зависимостей (для Elyx-колёс).
